
PERSONAL AI AGENT - DESKTOP EDITION
BUILD SPECIFICATION
Version 1.0
Derived from: Autonomous Personal AI Agent Platform - Build Specification v2.0 (Enterprise)
Target: Claude Code / Codex / equivalent coding agent
Platform: Windows 11 (single user, single PC)

============================================================
0. BUILD INSTRUCTION
============================================================

Build a production-quality, single-user, local-first autonomous personal AI agent that runs on the user's own Windows 11 desktop.

It is the personal edition of the enterprise platform. Keep the enterprise security model, scaled to one person and one PC:
- one desktop application with ONE user interface (no separate admin portal)
- every administrative capability lives under a "Settings" button in the left navigation pane
- everything is configurable through the GUI; the user never has to edit a file, registry key or command line
- local sign-in with username + password, set by the user on first run
- password reset with PIN + recovery key
- all secrets and passwords stored locally in an encrypted vault protected by Argon2id and the PC's TPM 2.0 chip
- local LLM on the same PC
- connectors (V1): Local Outlook (classic), Microsoft 365 / Exchange Online, Web search + fetch
- persistent memory, missions, scheduled/event-driven tasks that continue while the app window is closed
- deterministic policy engine, tool gateway, approvals, budgets, kill switch, sandboxed code execution
- one unified, tamper-evident security log file (optionally forwarded to a SIEM)

IMPORTANT SECURITY PRINCIPLES (unchanged from enterprise):

1. The LLM may propose an action; it is NEVER the authority that permits it.
2. Every consequential action passes deterministic policy enforcement in the Gateway process.
3. Default deny.
4. Security is evaluated on data flow (context sensitivity), not only on individual actions.
5. Policy is re-evaluated at execution time.
6. If an action cannot be audited, it is not executed.
7. Security components are built before the capabilities they protect.
8. Secrets never enter the model context, the sandbox, logs, memory or notifications.

ADDITIONAL PRINCIPLES FOR THE DESKTOP EDITION:

9. There is a SECURITY FLOOR: a small set of protections the user cannot switch off in Settings (Section 5.4). Settings can make the agent more restrictive freely; loosening is limited, re-authenticated and audited.
10. If the PC cannot provide a required isolation feature (e.g. a sandbox), the dependent capability is disabled and the UI says why. It is never silently run without protection.
11. The app never needs administrator rights after installation, and never runs any component as SYSTEM or administrator.

------------------------------------------------------------

Kept (adapted to one PC):
- Tool Gateway, Policy Engine (default deny), data-flow/taint control, egress control, DLP
- approvals bound to exact payload, step-up re-authentication
- kill switch with defined semantics
- budgets, missions, tasks, durable queue, idempotency, OUTCOME_UNKNOWN

- file quarantine and scanning pipeline
- sandboxed code execution
- unified, hash-chained security log; optional SIEM forwarding

- red-team suite and security tests

Replaced:
- Corporate SSO/MFA -> local username + password, quick-unlock PIN, recovery key, TPM-backed keys
- Admin Portal -> "Settings" in the single UI
- Secrets manager/KMS -> local encrypted vault (Argon2id + TPM 2.0 + AES-256-GCM)

Dropped (not applicable to a single user):
- multi-tenancy, SCIM, RBAC roles, admin/auditor roles, HA deployment, dual control

============================================================
1. PRODUCT VISION
============================================================

A private assistant on the user's own PC that keeps working while the user is away (as long as the PC is on and the user stays signed in to Windows, even if Windows is locked).

Examples:
- "Every morning at 7:30, summarize important emails and list what needs action."
- "Search my Outlook archive for the vendor contract discussion from 2023."
- "Research local LLM news overnight and prepare a report."
- "Remember how I like these reports."
- "Keep my API keys safe and use them only for the tools I allow."

Intent becomes: mission -> plan -> tasks -> gateway-controlled tool calls -> verification -> output -> (optional) memory.

2.2 Responsibilities

pa-ui.exe
- renders the single UI; holds no long-term secrets
- talks only to pa-gateway over IPC
- WebView2 locked down: no remote content, strict CSP, no navigation away, devtools disabled in release builds, no Node/filesystem APIs exposed

pa-gateway.exe (security core; the ONLY process with keys and network)
- vault and key management
- authentication (password, PIN quick-unlock, recovery)
- Tool Gateway (all tool calls), Policy Engine, DLP, egress filter
- connector adapters (M365 via Graph, web), orchestration of the Outlook worker
- approvals, budgets, kill switch
- audit writer and unified security log
- backups
- tray icon ("Open", "Pause agent", "Stop everything", "Lock")

pa-core.exe (agent runtime; no keys, no network)
- agent loop, planner, context manager (taint tracking), memory, skills
- missions, tasks, scheduler
- calls pa-llm for inference and pa-gateway for every tool call
- cannot read the vault; receives only data the gateway releases

pa-llm (local model server; no network)
- bundled llama.cpp server (OpenAI-compatible) bound to 127.0.0.1 on a random port, protected by a random per-launch API key known only to pa-gateway and pa-core
- GGUF model files only (no pickle-based formats); SHA-256 verified before load

pa-outlook-worker.exe (no network)
- spawned by the gateway on demand
- reads classic Outlook through the Outlook Object Model, read-only operations only
- exits when idle

pa-parser.exe (no network)
- parses PDF/Office/images in an AppContainer with no capabilities, read-only input, memory/time limits

Sandbox (no network)
- runs model-written Python (Section 19)

2.3 Why this split
- A bug or prompt-injection in the agent runtime (pa-core) cannot reach secrets or the internet: it has neither.
- Parsing malicious files and running generated code happen in processes that are firewalled and privilege-reduced.
- The OS enforces the boundaries (process separation, pipe ACLs, firewall rules), not the LLM.

2.4 IPC security
- Windows named pipes; ACL grants access only to the current user's SID (and denies network logon SIDs).
- Pipe names include a random per-launch component.
- The server verifies the client process: image path under the install directory and a valid Authenticode signature from the product's publisher.
- A per-launch random token handshake is required on every connection.
- NO TCP listening sockets except pa-llm on 127.0.0.1 (API-key protected, random port). The app never runs a localhost web server for its UI.
- Messages are schema-validated (JSON Schema / pydantic) on receipt.

2.5 Installation layout
- Program files: C:\Program Files\PersonalAgent\ (per-machine install, write-protected for standard users so no process can tamper with binaries)
- Data: %LOCALAPPDATA%\PersonalAgent\ with NTFS ACL: current user (full), SYSTEM (full), inheritance removed, all others denied
- The installer (MSI, code-signed) is the only step needing admin rights: it installs binaries and creates the firewall rules and the per-user logon scheduled task.
- The app refuses to place its data folder inside a cloud-synced folder (OneDrive, Dropbox, Google Drive) and warns if BitLocker (or equivalent full-disk encryption) is off.

3. TECHNOLOGY BASELINE
============================================================

- UI: Tauri 2 (Rust shell) + WebView2 + React/TypeScript
- Gateway: Rust (recommended, memory-safe for the security core) or Python 3.12 with strict typing if the team prefers one language; the vault crypto must use vetted libraries either way
- Core runtime: Python 3.12, asyncio
- Local database: SQLite with SQLCipher (AES-256) for the vault DB and app DB
- Vector store: sqlite-vec (inside the encrypted database) or LanceDB with file-level encryption
- Crypto:
    - Argon2id (libsodium / argon2 reference)
    - AES-256-GCM or XChaCha20-Poly1305 (libsodium / RustCrypto / Windows CNG)
    - HKDF-SHA-256
    - HMAC-SHA-256 for the log chain
    - Windows CNG "Microsoft Platform Crypto Provider" for TPM-bound keys
- LLM runtime: bundled llama.cpp server (default). Optional: Ollama or LM Studio (see Section 20.4 for hardening requirements and warnings)
- Sandbox: Windows Sandbox (Windows 11 Pro/Enterprise/Education with virtualization enabled); fallback AppContainer + Job Object
- Outlook: Outlook Object Model (COM) from a separate worker process
- M365: Microsoft Graph via MSAL (public client, auth code + PKCE, system browser)
- Packaging: signed MSI; signed update packages
- Tests: pytest, cargo test, Playwright for UI

============================================================
4. IDENTITY, SIGN-IN AND KEY MANAGEMENT
============================================================

4.1 Concepts
- Username: the user's local display/login name for this app. Not a secret. One vault per Windows user account.
- Password: the primary secret. Required at every cold start (after reboot, Windows sign-out, hibernate, or app restart).
- PIN: a short code for (a) quick unlock after the app auto-locks, while the agent is still running, and (b) together with the recovery key, resetting a forgotten password. The PIN is bound to this PC's TPM.
- Recovery key: a long random key shown once at setup, to print or store offline. Used with the PIN to reset the password.

4.2 First-run setup wizard (GUI)

Step 1 - Welcome and checks
- Shows: Windows version, TPM 2.0 present and ready, BitLocker status, virtualization/Windows Sandbox availability, data folder location, disk space, GPU/NPU detection for the model.
- Blocks setup if TPM 2.0 is not usable. Warns (does not block) if BitLocker is off, with a "How to turn on" link.

Step 2 - Create account
- Username (3-64 characters)
- Password + confirm:
    - minimum 12 characters, maximum 256
    - strength meter (zxcvbn-style); must reach "strong"
    - checked against a bundled offline list of common/breached passwords
    - must not contain the username
    - paste allowed (password managers)
- Explanation text: "Your password encrypts everything. We cannot recover it for you."

Step 3 - Create PIN
- 6 to 12 digits by default; option "allow letters" for an alphanumeric PIN
- rejects trivial PINs (repeated digits, simple sequences such as 123456 or 654321, and other patterns from a bundled list of common PINs)
- must differ from the password
- the PIN is registered with the TPM (Section 4.4)

Step 4 - Recovery key
- A 160-bit random key displayed as 8 groups of 5 characters (Crockford Base32), e.g. 7K2QD-9XM4R-...
- Buttons: "Save as PDF" (prompts for location; recommends printing and deleting the file), "Copy" (clipboard excluded from history, auto-cleared after 30 s)
- The user must type back two random groups to confirm they recorded it.
- Clear warning box:
    "To reset a forgotten password you need BOTH your PIN and this recovery key, on THIS computer.
     If you forget your password AND lose either your PIN or this key, your data cannot be recovered.
     Keep an encrypted backup (Settings > Backup) - backups are restored with your password."

Step 5 - Local AI model
- choose from a curated list sized to the detected hardware, or "I'll add one later"
- download over HTTPS from an allowlisted source with published SHA-256; verify before use
- or import a local GGUF file (SHA-256 shown and recorded)

Step 6 - Connectors (optional now)
- all connectors are OFF by default; the user can connect them here or later in Settings > Connectors

Step 7 - Autonomy defaults
- choose a profile: "Cautious" (default), "Balanced". (There is no profile that removes the security floor.)

Step 8 - Backup
- choose a backup folder (external drive recommended) and schedule, or skip with a warning

Step 9 - Done
- shows a summary and a link to the "How your data is protected" help page

4.3 Key hierarchy

  Vault Master Key (VMK): 256-bit random, generated at setup.
     |
     +-- HKDF -> K_db     (SQLCipher key for app/vault database)
     +-- HKDF -> K_files  (wraps per-file random keys for My Files and artifacts)
     +-- HKDF -> K_log    (HMAC key for the unified log chain)
     +-- HKDF -> K_secret (encrypts user secrets in the Secrets vault, per-item keys)
     +-- HKDF -> K_ipc    (derives per-launch IPC tokens)

  The VMK is never stored in plaintext. It is stored only in these wrapped forms in vault.header (versioned, integrity-protected):

  W_pw    = AEAD( KEK_pw, VMK )
            KEK_pw = Argon2id(password, salt_pw)
            Argon2id parameters calibrated at setup to take >= 1 second on this PC,
            minimum memory 256 MiB, iterations >= 3, parallelism 4. Parameters stored in the header.

  W_reset = AEAD( KEK_reset, VMK )
            KEK_reset = HKDF( S_tpm || RKey_stretched )
              S_tpm          = a 256-bit secret decryptable ONLY by a non-exportable TPM key whose use requires the PIN
              RKey_stretched = Argon2id(recovery key, salt_rk) (moderate cost; the recovery key already has 160 bits of entropy)
            => opening W_reset requires THIS PC's TPM + the correct PIN + the recovery key.

  There is NO wrapped copy of the VMK that the PIN alone can open at rest. An attacker who copies the data folder needs the password, or (recovery key + this PC's TPM + PIN).

4.4 PIN and TPM
- At setup, the gateway creates a non-exportable RSA-2048 or ECC P-256 key in the TPM via the Microsoft Platform Crypto Provider, with the PIN as the key's usage authorization.
- S_tpm is encrypted to that key and stored in the header.
- The TPM's dictionary-attack protection limits PIN guessing in hardware (lockout after a small number of failures, increasing lockout time). The app additionally disables the PIN after 5 consecutive failures until the next password sign-in.
- If the TPM is cleared or the motherboard is replaced, the PIN and W_reset stop working; the password still works, and the user re-creates the PIN.

4.5 Unlock flows

Cold start (after reboot, sign-out, hibernate, app restart):
- username + password only -> Argon2id -> unwrap VMK -> gateway unlocked.

Quick unlock (after the UI auto-locked, agent still running):
- PIN only; valid only while the gateway process has stayed unlocked since the last password sign-in.
- Implementation: while the UI is locked, the VMK stays only in pa-gateway's protected memory (needed so missions can keep running). Quick unlock proves the user is present by performing a TPM operation with the PIN-authorized key (decrypting a fresh random challenge). A wrong PIN counts toward the TPM lockout and the app's 5-failure limit.
- If "Pause missions while Windows is locked" is ON, the stricter mode applies: on UI lock the gateway wipes the VMK from memory and unlocking requires the password.
- Quick unlock expires after a configurable maximum (default 24 hours since last password entry), after which the password is required.

Step-up (re-authentication for sensitive actions):
- Required for: revealing a stored secret, exporting data, changing security settings, approving high-risk actions, disconnecting/reconnecting connectors, restoring a backup, viewing the Transcript Store.
- Accepts PIN (default) or password; loosening security settings ALWAYS requires the password.
- A successful step-up is valid for 5 minutes (configurable 1-15) for the same category of action.

4.6 Reset and change flows

Forgot password:
1. Sign-in screen -> "Forgot password?"
2. Enter PIN (TPM verifies) and the recovery key.
3. Gateway opens W_reset -> VMK.
4. User sets a new password (same rules). W_pw is re-created with a new salt.
5. The recovery key is then ROTATED automatically: a new recovery key is generated and shown (the old one has now been used). W_reset is re-created.
6. All pending approvals are voided; the event is logged; a notice is shown on the Home screen at next sign-in.

Change password (known):
- Settings > Account & Security -> requires current password -> new password -> W_pw re-created.

Forgot PIN:
- Sign in with password -> Settings > Account & Security -> "Set new PIN" -> new TPM key, W_reset re-created with the existing recovery key (requires the recovery key; if lost, generate a new one - see below).

Lost recovery key:
- Sign in with password -> "Generate new recovery key" -> requires password + PIN -> old W_reset destroyed, new key shown and confirmed.

Forgot password AND lost PIN or recovery key:
- Not recoverable on this PC by design. The user may restore an encrypted backup only if they remember the password used for that backup. The UI states this plainly at setup and in Settings.

4.7 Brute-force and session protections
- Password attempts: exponential delay (1, 2, 4, 8 ... s, max 5 min) after 3 failures; persistent counter; every failure logged. Offline guessing is slowed by Argon2id.
- PIN attempts: TPM hardware lockout + app disables PIN after 5 failures.
- Recovery attempts: 5 failures -> recovery disabled for 1 hour; logged.
- Auto-lock UI after idle (default 10 min; range 1-60).
- Lock UI when Windows locks (default ON).
- On Windows sign-out, shutdown, restart or hibernate: all keys are wiped from memory; missions pause until the next password sign-in.
- On sleep: keys stay in memory only if BitLocker is on; otherwise wiped (default; configurable only toward "always wipe").
- Keys held in memory: locked pages (VirtualLock), encrypted in memory where supported (CryptProtectMemory), zeroized after use; crash dumps disabled for pa-gateway (WER exclusion); no swap of key material.
- Screens showing secrets use SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE) so they are excluded from screenshots/screen sharing.

4.8 Honest limits (shown in the in-app help)
- If malware runs as the user on the same PC while the vault is unlocked, it may capture keystrokes or the screen. Process separation, firewall rules and short unlock windows reduce this risk but cannot eliminate it. Keep Windows and Defender up to date.
- Physical access to an unlocked, signed-in PC is equivalent to access to the agent.

5.4 Security floor (cannot be turned off in Settings)
1. Sign-in with password at cold start; auto-lock exists (timeout adjustable, not disableable).
2. Vault encryption; secrets never reach the model, sandbox, logs, memory or notifications.
3. Tool Gateway + Policy Engine on every tool call; default deny.
4. Sending, forwarding or deleting email, and any external write, always require approval.
5. Model-generated code runs only in the sandbox; no host shell tool exists.
6. Untrusted content can never change settings, policies, connectors, memory trust or skills.
7. File quarantine and scanning for every ingested file.
8. RESTRICTED data can never be sent out.
9. Unified security log with integrity chain; actions stop if logging fails.
10. Kill switch always available in the top bar and tray.
11. Only pa-gateway may reach the network.

5.5 Rules for changing settings
- Tightening: immediate; logged.
- Loosening (e.g. enabling "Fetch any site", raising budgets, enabling Mail.Send capability): password required, a confirmation dialog that states the risk in plain language, 10-second read delay before "Confirm" is enabled, logged with before/after values.
- The agent has no tool that can read or change settings.

============================================================
6. SECRETS VAULT (YOUR PASSWORDS AND KEYS)
============================================================

6.1 Purpose
Store all of the user's secrets locally and safely:
- connector credentials (M365 refresh token, web search API key)
- any passwords, API keys, notes or tokens the user chooses to keep (a personal password manager)

6.2 Storage
- Each secret item is encrypted with its own random key (AES-256-GCM / XChaCha20-Poly1305); item keys are wrapped with K_secret.
- Items live inside the SQLCipher database (double encryption).
- Metadata (title, type, tags, allowed-tool bindings, created/updated, last used) is also encrypted.

6.3 GUI (left pane > Secrets)
- list with search, tags and types (Password, API key, Token, Note, Card-like data)
- add/edit with password generator (length, character sets)
- reveal value: step-up required; value auto-hidden after 20 s; window excluded from screen capture
- copy value: step-up required; the clipboard entry is excluded from Windows clipboard history/cloud sync and auto-cleared after 30 s (configurable 10-120 s)
- item history (previous versions, encrypted), restore a version
- "Used by" bindings: which connector/tool may use this secret (see 6.4)
- health report: weak, reused, old secrets (computed locally)
- import from CSV (warned: delete the CSV afterwards; offered secure delete) and export (encrypted archive only, step-up + password)

6.4 How the agent may use a secret
- The agent never sees secret values. There is no tool that returns a secret to pa-core.
- A secret can be BOUND to a specific tool/connector (e.g. "Web search API key -> web.search"). The gateway injects it into the outbound request at execution time, in memory only.
- Unbound user secrets (e.g. a bank password) are never used by the agent at all. There is no "fill this password into a website" capability in V1.
- Outbound DLP scans every request and response for any stored secret value (via keyed hashes of secrets) and blocks/redacts on match; a match is a security event.

============================================================
7. TOOL GATEWAY AND POLICY ENGINE
============================================================

7.1 Tool definition
Each tool: name, version, connector, input/output schema, argument constraints, side-effect type (NONE / INTERNAL_WRITE / EXTERNAL_WRITE / EGRESS), risk, output sensitivity, rate limit, timeout, approval rule, bound secret (if any), definition hash (pinned).

V1 tools:
- outlook_local.list_folders, outlook_local.search, outlook_local.get_message, outlook_local.get_attachment, outlook_local.calendar_read
- outlook_local.create_draft (optional, off by default)
- m365.search_mail, m365.get_message, m365.get_attachment, m365.calendar_read
- m365.create_draft (optional, off by default)
- m365.send_mail (optional capability, off by default; ALWAYS requires approval)
- web.search, web.fetch
- files.read, files.write (My Files; by file ID)
- python.run (sandbox only)
- notify.user (Windows toast; content-level rules apply)

7.2 Invocation sequence (every call; no bypass)

  kill switch check
  -> schema validation
  -> caller identity (pa-core instance + task/mission IDs from gateway's own records)
  -> connector effective state (Section 8.2), incl. chat vs mission flag
  -> resource ownership / scope (file IDs, folder allowlists)
  -> argument constraints (recipients, domains, sizes)
  -> data-flow check against context sensitivity (Section 13)
  -> policy decision (default deny)
  -> budget check
  -> DLP / egress check
  -> approval if required (payload-hash bound)
  -> policy re-check immediately before execution
  -> audit "about to execute" (must succeed)
  -> execute (egress filter / Outlook worker / sandbox)
  -> validate + classify result
  -> audit "result"
  -> return to pa-core labelled UNTRUSTED DATA

7.3 Policy engine
- Rules as code (embedded OPA/Rego or Cedar, or a typed rule module), versioned; defaults ship with the app and are unit tested.
- User edits in Settings produce rule overlays that can only tighten floor rules.
- Decisions: ALLOW / DENY / REQUIRE_APPROVAL / SANDBOX. Conflict: DENY > REQUIRE_APPROVAL > SANDBOX > ALLOW.
- Engine failure -> DENY.
- Every decision logged with rule version.

============================================================
8. CONNECTOR FRAMEWORK AND CONNECTOR SETTINGS
============================================================

8.1 V1 connectors
- outlook_local  (classic Outlook on this PC)
- m365           (Microsoft 365 / Exchange Online via Microsoft Graph)
- web            (web search + fetch)
Future connectors (e.g. ChiRAG, IMAP, calendars, other APIs) plug into the same framework with their own adapter, tool definitions and tests. No framework changes should be needed.

8.2 Effective state (computed by the gateway on every call)

  USABLE = connector toggle ON
       AND NOT "Pause all connectors"
       AND NOT agent paused / emergency stop
       AND connection valid (token present / Outlook available)
       AND context flag allows it:
             chat      -> "Use in chat" ticked
             mission   -> "Use in missions" ticked

8.3 Behavior when switched OFF (Settings > Connectors)
1. Saved and logged before the toggle shows "Off".
2. New calls denied within 2 seconds (single PC target).
3. In-flight calls cancelled; late results discarded, never added to context or memory.
4. Tasks needing it -> WAITING_FOR_RESOURCE ("turned off by you"); no retry storms; mission shows a warning.
5. The agent may not reach the same data another way (e.g. with m365 OFF, web.fetch to outlook.office.com / graph.microsoft.com is denied).

"Disconnect":
- everything above, plus revoke/delete stored tokens (M365: delete refresh token; call Microsoft sign-out/revoke endpoint where available), purge connector caches.

Switch ON again:
- if still connected: immediate
- if disconnected: re-connect flow with step-up
- suspended missions resume only when the user clicks "Resume"

============================================================
9. LOCAL OUTLOOK CONNECTOR
============================================================

9.1 Scope
Read the user's classic Outlook for Windows (including PST archives and cached OST data) on the same PC. New Outlook for Windows does not support the Object Model; the UI detects this and suggests the M365 connector instead.

9.2 Design
- pa-gateway spawns pa-outlook-worker.exe on demand, as the same user, at medium or lower integrity where Outlook allows it, with firewall outbound blocked.
- The worker exposes a fixed set of read operations over a private pipe to the gateway only. It never receives prompts or model output.
- The worker uses the Outlook Object Model via COM, read-only. It must NOT suppress, bypass or auto-click the Outlook Object Model Guard or any security prompt. If Outlook shows a security prompt (e.g. antivirus not reported healthy), the operation waits for the user or fails with a clear message.
- The worker does not start Outlook silently if it is closed unless the user enabled "Start Outlook when needed" (off by default); otherwise the task waits ("Outlook is closed").

9.3 Operations
Read-only (V1): list_folders, search (query, folder scope, date range, max results), get_message (plain text body; HTML stripped; images not loaded), get_attachment (streamed straight into quarantine), calendar_read.
Optional (off by default): create_draft (marked "AI Draft"; recipients limited to the original thread participants unless approved).
Not supported: send, forward, delete, move, rules, contacts export, account settings.

9.4 Scope controls (Settings > Connectors > Local Outlook)
- folder allowlist/denylist (defaults exclude Deleted Items, Junk, and any folder the user marks Private)
- include PST archives (per file, on/off)
- max items per request, max body size, max attachment size, date range limit
- items with Microsoft sensitivity labels at the highest level: excluded or metadata-only (default metadata-only)

9.5 Data handling
- results are UNTRUSTED, source=outlook_local, sensitivity from label else CONFIDENTIAL
- no persistent cache of message bodies outside the encrypted database; transient buffers in memory only

============================================================
10. MICROSOFT 365 / EXCHANGE ONLINE CONNECTOR
============================================================

10.1 Authentication
- MSAL public-client flow: authorization code + PKCE in the system browser (not an embedded webview), redirect to a loopback or custom-scheme URI handled by the gateway.
- Uses an Entra ID app registration: either the user's organization's registration (preferred when the organization requires admin consent) or one the user creates. The Settings screen guides through entering the Client ID and Tenant ID; no client secret is used (public client).
- Refresh token stored only in the vault; access tokens in gateway memory only.

10.2 Scopes (incremental; least privilege)
- Default: User.Read, Mail.Read, Calendars.Read, offline_access
- Requested only when the user enables the feature in Settings:
    - Mail.ReadWrite (for drafts)
    - Mail.Send (for approved sending; each send always requires approval)
- The granted scopes are shown in plain language in Settings.

10.3 Operations
- search_mail, get_message, get_attachment (into quarantine), calendar_read
- create_draft (optional): marked "AI Draft" (category + visible note), recipients limited to the thread unless approved
- send_mail (optional): approval required every time, payload-hash bound, idempotent (Section 17.3)
- no delete / move / rules / forwarding in V1

10.4 Data handling
- untrusted; sensitivity from Microsoft Purview labels when present, else CONFIDENTIAL
- Graph endpoints are on the egress allowlist only while the connector is ON

============================================================
11. WEB SEARCH AND FETCH CONNECTOR
============================================================

11.1 Search
- provider selectable in Settings > Web Access (e.g. Brave Search API, Bing Web Search, or a self-hosted SearXNG URL); API key stored in the vault and bound to web.search
- the query text is EGRESS: it is checked against context sensitivity and DLP before sending

11.2 Fetch (egress filter inside pa-gateway)
- HTTPS only by default
- domain allowlist by default; "Fetch any site" mode optional (off)
- SSRF protection: resolve DNS in the gateway; block private, loopback, link-local, CGNAT, multicast and metadata ranges (IPv4/IPv6, incl. IPv4-mapped); pin the resolved IP; re-check every redirect (max 5); block non-standard ports unless allowlisted; block file://, ftp://, data: etc.
- size limit (default 5 MB), timeout (default 20 s), content-type allowlist (HTML, text, PDF, JSON)
- no JavaScript execution; HTML converted to text by the gateway; PDFs go to the file pipeline
- cookies are never sent; no logged-in browsing; user browser profiles are never read
- responses are UNTRUSTED; hidden text, comments, metadata labelled

============================================================
12. PROMPT INJECTION DEFENSE
============================================================

All external content is untrusted: mail (Outlook, M365), calendar invites, web pages, search results, files, OCR text, sandbox output, tool results.

- Trusted instructions (system prompt, user settings, policies) are kept separate from untrusted data; untrusted data is placed only in delimited data sections with source and sensitivity labels.
- Injection detection (heuristics + optional small classifier) raises a flag and can lower the task's rights, but is never the only defense; the gateway/policy prevent unauthorized actions regardless.
- Tasks triggered by incoming mail from outside run with reduced rights (Section 16.3).

============================================================
13. DATA SENSITIVITY AND DATA-FLOW CONTROL
============================================================

13.1 Levels: PUBLIC < INTERNAL < CONFIDENTIAL < RESTRICTED

Defaults (editable to stricter in Settings > Rules & Safety):
- Outlook / M365 mail and calendar: CONFIDENTIAL (or the item's sensitivity label if higher)
- My Files: INTERNAL (user can label any file higher)
- Secrets: RESTRICTED (never enter context anyway)
- Web content: PUBLIC

13.2 Propagation
- Derived items (summaries, drafts, memories, reports, sandbox output) inherit the highest input level.
- The model cannot lower a label; only the user can, with step-up; logged.

13.3 Context high-water mark
Each task/chat tracks the highest sensitivity that has entered its context.

  high-water mark | web.search / web.fetch                   | external write (send mail, etc.)
  ----------------+------------------------------------------+-------------------------------------
  PUBLIC          | allowed (allowlists apply)               | approval
  INTERNAL        | allowed                                  | approval
  CONFIDENTIAL    | approval showing exact query/URL         | approval with password step-up
  RESTRICTED      | denied                                   | denied

- The planner may start a clean sub-task for public web research; the gateway passes it only approved public inputs.

============================================================
14. EGRESS AND DLP
============================================================

14.1 Egress channels (all checked)
web search queries, fetched URLs, M365 send/draft recipients and content, notifications (toasts, email-to-self), log forwarding to SIEM (metadata only), update checks (no user data), model downloads (no user data), file names/metadata sent anywhere.

14.2 Enforcement layers
1. OS: Windows Defender Firewall per-program rules - outbound blocked for pa-core, pa-llm, pa-outlook-worker, pa-parser and the sandbox; only pa-gateway (and the signed updater) may connect out. The Security checks panel verifies the rules at every start and blocks startup of the agent runtime if they are missing (offers "Repair").
2. Application: the gateway egress filter (allowlists, SSRF rules, sizes, rate limits).
3. Content: DLP patterns (built-in: secret values from the vault, API key formats, card numbers, IBAN/account formats, national ID formats configurable by the user) + context sensitivity rules.
4. Volume: egress bytes/records budgets per task and per day.

14.3 UI rendering
- Chat never auto-loads remote images; links require a click; the WebView cannot navigate to remote pages.

============================================================
15. FILE SECURITY PIPELINE
============================================================

Sources: user upload, Outlook attachment, M365 attachment, web downloads (PDF), sandbox output, agent output.

  ingest -> QUARANTINE (encrypted, not usable)
         -> validate (type sniffing vs extension, size, archive depth/ratio/count limits)
         -> Microsoft Defender scan (via AMSI / MpCmdRun custom scan) + macro/active-content detection
         -> safe extraction / disarm (text + page images; macros and embedded objects removed)
         -> classify (inherit source label)
         -> parse in pa-parser (AppContainer, no network, time/memory limits)
         -> available to the agent as UNTRUSTED data

- Failing files stay in quarantine (Settings > Files & Storage > Quarantine), with reason; the user can delete them.
- Hidden content (white/tiny text, off-page text, comments, metadata, alt text, OCR text in images) is extracted but labelled.
- Files are never opened with their default Windows handler by the app.

============================================================
16. MISSIONS, TRIGGERS AND SCHEDULING
============================================================

16.1 Missions
Fields: objective, schedule/trigger (with timezone), allowed connectors/tools, allowed in overnight runs, budgets, model (optional pin), output format, notification level, missed-run policy (SKIP / RUN_ONCE default / RUN_ALL), resource-wait timeout.
Lifecycle: DRAFT, ACTIVE, PAUSED, SUSPENDED, WAITING_APPROVAL, COMPLETED, FAILED, CANCELLED.
Only the user creates/activates/widens/resumes missions (agent can propose).

16.2 Running while away
- pa-gateway and pa-core start at Windows sign-in via a per-user scheduled task and keep running with only the tray icon when the window is closed.
- Missions run while the user is signed in to Windows, including while Windows is locked (unless "Pause missions while Windows is locked" is ON).
- Missions do not run while the PC is off, hibernated, or signed out; they catch up per missed-run policy at the next password sign-in.
- Optional: keep awake during mission windows; wake timers for scheduled missions (requires the user to be signed in; if keys were wiped the run waits for sign-in).

16.3 Triggers
Types and trust:
- USER (from chat/UI): full rights within policy
- SCHEDULE: the mission's allowed tools
- LOCAL_EVENT (new file in My Files): mission tools
- EXTERNAL_EVENT (new mail): reduced rights - read-only, no egress, no drafts to outside recipients, memory writes at most INFERRED
Controls: sender/domain/folder filters, rate limit (default 20 runs/hour; excess batched), and each triggered run consumes budget.

16.4 Scheduling details
- IANA timezone, DST-safe
- catch-up runs jittered and rate-limited
- single scheduler instance (lock file + database lease)

============================================================
17. TASKS, DURABILITY AND IDEMPOTENCY
============================================================

17.1 Task states
CREATED, PLANNING, QUEUED, RUNNING, WAITING_FOR_RESOURCE, WAITING_FOR_APPROVAL, SUSPENDED, VERIFYING, OUTCOME_UNKNOWN, COMPLETED, FAILED, CANCELLED, TIMED_OUT.

17.2 Durability
- SQLite (WAL mode, inside SQLCipher) is the system of record for tasks and queue; state persisted transactionally on every transition.
- After crash/restart/sign-in, recoverable tasks resume.

17.3 Idempotency
- Every side effect has key = hash(task_id + action_id + payload_hash); outbox pattern (save intent -> act -> record outcome).
- M365 send: set a unique internet message header containing the key; after a crash, search Sent Items for it.
- If the outcome cannot be determined: OUTCOME_UNKNOWN; shown on Home; never retried automatically.

============================================================
18. BUDGETS
============================================================

Per task and per day (user-level), editable in Settings > Autonomy & Budgets:
runtime, LLM tokens, GPU time, tool calls, web requests, files processed, output size, external writes, egress bytes/records, retries, sub-tasks, depth (default 3), concurrent tasks (default 3).

On exhaustion: stop -> save state -> report (Home + log).
Interactive chat has priority over background missions on the local model.

Defaults (Cautious profile):
- per task: 30 min, 200k tokens, 100 tool calls, 30 web requests, 20 files, 0 external writes without approval, 100 KB egress
- per day: 4 h runtime, 2M tokens, 150 web requests, 1 MB egress

============================================================
19. SANDBOXED CODE EXECUTION
============================================================

19.1 Preferred: Windows Sandbox
- available on Windows 11 Pro/Enterprise/Education with virtualization enabled
- disposable Hyper-V-isolated environment launched from a generated .wsb configuration:
    - networking disabled
    - vGPU disabled, audio/video input disabled, printer and clipboard redirection disabled
    - one mapped folder read-only (inputs copied in by the gateway, by file ID) and one mapped output folder
    - a pinned, signed portable Python with approved packages
    - run command executes the script; environment is destroyed after completion
- time limit enforced by the gateway (terminate sandbox)

19.2 Fallback: AppContainer + Job Object
- used if Windows Sandbox is unavailable (e.g. Windows 11 Home)
- Python runs in an AppContainer with NO capabilities (no network, no user folders), low integrity, inside a Job Object limiting CPU, memory, process count, and wall time; working directory is a per-run folder with an ACL for that AppContainer only; firewall outbound blocked
- the UI labels this mode "Standard isolation" and Windows Sandbox as "Strong isolation"

19.3 Neither available
- python.run is disabled; Settings explains how to enable Windows Sandbox.

19.4 Rules
- only files explicitly granted for the task are copied in
- all outputs are untrusted; files go through the file pipeline; outputs inherit the highest input sensitivity
- no secrets, tokens, vault paths or user profile paths are ever visible inside the sandbox

20. LOCAL LLM RUNTIME
============================================================

20.1 Built-in runtime (default)
- bundled llama.cpp server, started by pa-gateway with: --host 127.0.0.1, random port, --api-key <random per launch>, no model download capability at runtime
- firewall outbound blocked for the process
- GGUF model files only; SHA-256 verified at load; model registry records name, source URL, license, quantization, size, hash, date

20.2 Model management (Settings > AI Model)
- curated catalog with hashes; download via the gateway over HTTPS from allowlisted hosts; verify; then "Test model" (red-team smoke test + quality checks) before it can become default
- manual import of a GGUF file (hash recorded; warning shown)

20.3 Routing
- the LLM Router in pa-core picks the model by role (fast / standard / reasoning / vision) per Settings; the model never selects endpoints
- missions may pin a model; a model change requires re-test before pinned missions use it

20.4 Optional external runtimes (Ollama / LM Studio)
- allowed only if: bound to 127.0.0.1 only, browser origins restricted (e.g. OLLAMA_ORIGINS not set to "*"), and the app's health check confirms it is not reachable from the network
- the UI marks these as "Reduced isolation" because they are separate programs that do not use the app's per-launch API key and any local process can call them
- the app never lets these runtimes pull models automatically

20.5 Privacy
- prompt/response logging in the runtime is disabled; transcripts needed for troubleshooting are stored only in the encrypted Transcript Store (Section 25.5)
- no cross-conversation KV cache persistence to disk

21. MEMORY
============================================================

Types: working, episodic, semantic, procedural, preferences, project.
Record fields: id, type, content, source, provenance (message/file IDs), trust level, confidence, sensitivity, created, last verified, status, expiry.
Storage: inside the encrypted database; embeddings also encrypted.

Trust levels:
- TRUSTED: what the user states in the UI
- VERIFIED: repeated user-initiated actions, or user-confirmed
- INFERRED: model inference (shown in "Proposed memories")
- UNTRUSTED: mail, web, files, API content

Rules:
- only TRUSTED/VERIFIED may change preferences automatically; agent-initiated actions never count as evidence
- memory can never change settings, policies, connectors, skills or security
- at use time, memories derived from a source the user has since deleted or disconnected are hidden
- deleting a source cascades to derived memories and embeddings

============================================================
22. SKILLS
============================================================

- reusable workflows with declared tools, connectors, risk, max steps, timeout, schemas
- the agent may propose; the user reviews the full definition and diff; approval requires step-up (password for skills using write/egress tools)
- skills are scanned for embedded instructions aimed at the model before review
- versioned, signed locally (HMAC with a vault key), audited on every run
- a skill cannot declare permissions beyond current policy; skills whose connectors are OFF cannot run

============================================================
23. APPROVALS
============================================================

- Shown in Approvals with exact payload, sensitivity, destination, risk, origin, expiry (default 24 h; high risk 1 h).
- Bound to SHA-256 of the exact payload + destination; any change voids it; single-use.
- High-risk approvals require step-up (PIN by default; "password only" option in Settings).
- Policy, kill switch and connector state are re-checked immediately before execution.
- Approvals are never granted from a notification, email or link; only inside the unlocked app.
- Fatigue controls: rate limit on approval requests; similar low-risk requests batched; a warning if approvals are being accepted in under 2 seconds repeatedly.

Always need approval (floor): sending email, any external write, fetching/searching while the context is CONFIDENTIAL, running a newly proposed skill for the first time, enabling a mission that uses write tools.

============================================================
24. KILL SWITCH (EMERGENCY STOP)
============================================================

Controls: top bar "STOP ALL", tray menu, global hotkey, Settings > Emergency Stop.
Levels: pause agent; stop all tasks; disable all connectors; disable web access; disable sandbox; STOP ALL (everything).

Semantics:
- state stored in the database and read by pa-gateway before every step and tool call
- new tool calls blocked within 2 seconds
- in-flight calls cancelled; late results discarded
- sandbox terminated; Outlook worker terminated
- scheduled runs do not fire; queued tasks held (not deleted)
- pending approvals voided
- STOP ALL additionally terminates pa-core and pa-llm
- release requires the password; logged

============================================================
25. UNIFIED SECURITY LOG
============================================================

25.1 One file
- All security-relevant events from all components are written by the single Audit Writer inside pa-gateway to ONE active file:
    %LOCALAPPDATA%\PersonalAgent\logs\agent-security.jsonl   (location changeable in Settings)
- JSON Lines, UTF-8, versioned schema with OCSF-aligned field names.
- Rotation by size/age (default 100 MB or 7 days); the active path never changes; rotated segments are sealed and kept per retention (default 1 year).

25.2 Integrity
- each event: sequence number, prev_hash, and an HMAC-SHA-256 chain value keyed with K_log (so the chain cannot be recomputed without the vault key)
- each rotated segment ends with a seal record
- "Verify integrity" in Settings and on every start; failures raise a security event on Home
- log folder ACL: current user only; files opened append-only by the writer

25.3 Fail closed
- consequential actions write "about to execute" first; if the write fails, the action does not run
- bounded durable spool for short disk hiccups

25.4 Content minimization
- metadata only: IDs, hashes, sizes, sensitivity, decisions, connectors, tools, results
- never: secret values, passwords, PINs, recovery keys, tokens, email bodies, file contents, full prompts
- redaction filter + secret scanner (keyed hashes of vault secrets) before write; failures become "[REDACTED:ERROR]", the event is still written

25.5 Transcript Store
- full prompts/completions/tool payloads (for "why did the agent do this?") are kept in the encrypted database, referenced by transcript_id in the log
- viewing requires step-up; retention default 30 days

25.6 SIEM (optional)
- off by default; Settings > Logs & SIEM: syslog-TLS (RFC 5425) or HTTPS forwarding with certificate pinning, test button, forwarding lag indicator
- any standard shipper (Splunk UF, Elastic Agent, Fluent Bit, Wazuh, Sentinel AMA) can also tail the file path; a read-only ACL entry for a chosen local account can be added through the GUI (step-up)

25.7 Events logged
sign-in success/failure, quick unlock, step-up, recovery use, password/PIN/recovery key changes, lock/unlock, settings changes (before/after), connector ON/OFF/connect/disconnect/scopes, every policy decision, every tool call (about-to-execute + result), egress with destination/size/DLP result, approvals lifecycle, kill switch activations/releases, mission/task transitions, file ingest/scan/quarantine/delete, secret created/revealed/copied/used-by-tool (never the value), memory lifecycle, skill lifecycle, sandbox runs/violations, model load/verify/change, backup/restore, updates, log rotation/seal/verify results, firewall/security-check results.

27. BACKUP AND RESTORE
============================================================

- Backup file (.pabk): encrypted archive of the database, files, settings, skills, policies, sealed logs (optional)
- Encrypted with a random backup key (AES-256-GCM); the backup key is wrapped with Argon2id(password) - restore needs the password used at backup time
- Stored in a user-chosen folder (external drive recommended; cloud folders allowed for BACKUPS only, since they are encrypted, with a warning)
- Schedule daily/weekly; versions kept (default 7); "Verify backup" performs a full test decrypt and integrity check
- Restore: step-up + password; restoring onto a new PC requires setting a new PIN and generates a new recovery key (TPM-bound parts are not portable by design)
- Secrets are never exported in plaintext

Configurable retention: chats, Transcript Store, task history, mission outputs, files, artifacts, memories, quarantine, logs, backups.

- "Delete everything": password + typed confirmation; wipes keys first (crypto-erase), then deletes files

31. SECURITY TESTING
============================================================

Automated tests (CI) for:

Authentication and vault
- wrong password/PIN/recovery lockouts and delays
- vault header tampering detected (AEAD failure -> refuse)
- copy of the data folder to another PC cannot be opened with PIN + recovery key; only with the password
- forgot-password flow requires BOTH PIN (TPM) and recovery key; rotates recovery key afterwards
- keys wiped on sign-out/hibernate; missions pause
- secrets never appear in logs, crash output, IPC traces, model context or sandbox (canary secrets)
- clipboard auto-clear and history exclusion

Process and OS isolation
- pa-core, pa-llm, pa-outlook-worker, pa-parser, sandbox cannot open outbound connections (firewall test)
- named pipes reject other users and unsigned client processes
- pa-llm rejects requests without the per-launch API key
- data folder ACL denies other local users

Connectors
- OFF toggle blocks calls within 2 s in chat and missions; late results discarded
- no alternate-path access (web.fetch to Graph/OWA when m365 is OFF)
- Outlook worker has no send/delete capability; does not bypass Object Model Guard
- M365 requests only enabled scopes

Prompt injection and exfiltration
- malicious emails (Outlook and M365), calendar invites, web pages, PDFs with hidden text, OCR text
- confidential data in search queries, URLs, notifications, draft recipients, file names
- chained allowed actions

Files
- malware (EICAR), macro documents, decompression bombs, malformed PDFs, masquerading executables, HTML/SVG preview scripts

Agent
- infinite loops, sub-task explosions, budget exhaustion, malicious skill proposals, memory poisoning via induced repetition, trigger flooding by email

Web
- SSRF (private IPs, IPv6, redirects, DNS rebinding), oversized responses, non-HTTPS

Audit
- "about to execute" precedes every action; action blocked if log write fails
- chain verification detects edits, deletions, reordering

Kill switch
- each level enforced within 2 s with defined in-flight behavior; release needs password

============================================================
32. RED-TEAM SUITE
============================================================

- adversarial corpus stored in the repo (/security/redteam)
- each attack run N=20 times per release and per model change
- release FAILS if in any run an unauthorized action executed, protected data reached an unauthorized destination, or settings/memory trust changed from untrusted content
- model-level "attack success" rate tracked as a metric; the deterministic outcome is the gate
- also runs as "Test model" in Settings (a short subset) before a new model can become default

34. ACCEPTANCE CRITERIA
============================================================

V1 is complete only when:

Sign-in and secrets
1. First-run wizard sets username, password, PIN and recovery key entirely through the GUI.
2. Cold start requires the password; quick unlock uses the PIN; auto-lock works.
3. Forgot password works only with PIN + recovery key on this PC, and rotates the recovery key.
4. Copied data folder cannot be opened without the password.
5. Secrets vault stores, reveals (step-up), copies (auto-clear) and binds secrets; the agent never sees values.

Single UI
6. One window; left pane with everyday areas; every setting reachable under the Settings button; no file editing needed.
7. Security floor items cannot be disabled; loosening requires password and is logged.

Isolation
8. Only pa-gateway can reach the network (verified by test and by the Security checks panel).
9. Model-written code runs only in Windows Sandbox or AppContainer; otherwise disabled.
10. pa-llm is loopback-only and API-key protected.

Connectors
11. Local Outlook read/search works read-only without bypassing Outlook security prompts.
12. M365 read/search works with least-privilege scopes; send (if enabled) always requires approval.
13. Web search/fetch works through the egress filter with SSRF protection.
14. Turning any connector off takes effect within 2 s in chat and missions; Disconnect revokes tokens.

Agent safety
15. Missions run while the window is closed and Windows is locked; pause on sign-out/hibernate and catch up.
16. Tool authorization is deterministic, default deny, re-checked at execution.
17. Prompt injection cannot grant rights, change settings or cause sends.
18. Context sensitivity rules govern search/fetch/send.
19. Approvals are payload-bound and step-up protected.
20. Budgets stop runaway tasks; OUTCOME_UNKNOWN is never auto-retried.
21. Kill switch works within 2 s, independent of the model.

Audit and recovery
22. All security events of the app are in one HMAC-chained JSONL log file; integrity verification works; no secrets or content in it.
23. Optional SIEM forwarding works.
24. Encrypted backup and restore (including to a new PC) tested.
25. Red-team suite passes the deterministic gate.

35. IMPLEMENTATION RULES FOR CLAUDE/CODEX
============================================================

1. Build the security spine first; keep the app runnable at every milestone.
2. Use vetted crypto libraries only; never implement primitives.
3. Never log, print or send secrets, PINs, passwords, recovery keys or tokens.
4. Never give pa-core network access or vault access.
5. Never add a shell/command tool for the model.
6. Never bypass Outlook security prompts.
7. Never open a TCP listener except pa-llm on loopback with an API key.
8. Every setting has a GUI control; defaults live in code, user values in the encrypted database.
9. Default deny for tools, connectors, domains.
10. Fail closed when policy, logging, vault or isolation checks fail.
11. Tests for every security-sensitive component in the same change.
12. Mock adapters only in test builds; release builds cannot load them.
13. No telemetry leaves the PC.
14. Keep connectors pluggable so ChiRAG and others can be added without framework changes.

37. ASSUMPTIONS AND OPEN ITEMS
============================================================

Assumptions made in this spec (change them if they are wrong):
1. One user per Windows account; no sharing of the agent between people.
2. The PC has TPM 2.0 enabled (Windows 11 requirement) and ideally BitLocker on.
3. "Strong isolation" for Python needs Windows 11 Pro/Enterprise/Education; on Home the AppContainer fallback is used.
4. Microsoft 365 access may require the organization's IT to approve the app registration (admin consent) and may be subject to organization policies (Conditional Access, device compliance). The connector shows the exact Microsoft error if blocked.
5. Automating classic Outlook may be restricted by the organization's endpoint policies; the app does not work around such restrictions.
6. Local model quality depends on hardware; a GPU with >= 8 GB VRAM or a recent NPU/Apple-class performance is recommended for comfortable speed.
7. Overnight missions require the PC to stay on and the user to stay signed in to Windows (locked is fine).
8. ChiRAG and other connectors are out of scope for V1 and will be added through the connector framework.
