1. What is ChiRAG Agent?

ChiRAG Agent (folder name Personal Agent) is a private AI assistant that lives on your Windows PC. You talk to it in a window; it can answer, remind, read your Outlook mail, read files and folders you allow, look at pictures and scans, listen to your voice, search the web (only if you allow) and run routines on a schedule.

The AI model itself (for example Qwen or Gemma running in Ollama) only suggests what to do. A strict program called the gateway decides what is really allowed, writes everything to a tamper-evident log, and keeps your passwords and keys. That idea is repeated everywhere in the design: "the model proposes, the gateway decides".

Local first
Your data stays on the PC. Nothing is sent anywhere unless you set up a web provider or a remote model, and the app tells you when it does.
Security first
Encrypted database, key protected by the PC's TPM chip, no shell access for the AI, approvals for risky actions, kill switch (STOP ALL).
Plain controls
Every setting has a button or switch in the window. The AI cannot change settings.

2. The big picture (who talks to whom)

  • Solid arrows = normal talking. The window and the gateway talk through a Windows named pipe (a private local channel, not a network port).
  • Dotted arrows = the gateway reaching out to models and the internet. Only the gateway may do that; pa-core has no network and no keys.
  • Helpers (parser, Outlook worker, sandbox) are separate small programs started for one job so a bad file or a bug cannot touch the rest.

3. The programs and what each is allowed to do

4. Life of one chat message

1. You type a message (or speak) and press Send in the window.
↓
2. pa-ui sends chat.send through the named pipe to the gateway.
↓
3. Gateway checks you are signed in, saves the message to the encrypted database and the session log (rule: nothing reaches a model unless it is logged first), indexes it for History search, starts a task.
↓
4. pa-core picks the task up, builds the prompt: system rules + your memory + shared files list + the conversation.
↓
5. pa-core asks the gateway to call the model. The gateway sends it to Ollama (/v1, JSON-schema answer) and streams the words back to your window. Empty answer? It retries without the JSON constraint, then through Ollama's native API.
↓
6. The model answers with JSON: either final (the answer) or tool (what it wants to use, with arguments)
↓
7. If a tool: pa-core asks the gateway tools.invoke. The gateway runs its safety sequence (next section), runs the tool, returns the result (marked untrusted data). Back to step 5 until the model says final.
↓
8. Final answer is saved, shown with its sources (web, Outlook, files...), a Windows notification is sent if the window is not in front, and the run's steps are kept for the Steps panel.

Small note: every model call, tool call and result is also written to the HMAC-chained audit log (each record contains the hash of the previous one, so edits are detectable).

5. How a tool call is checked (the gateway's safety sequence)

Web access has one extra rule: the first web search or page fetch in a chat asks you once, and the answer lasts for that chat until you sign out or restart.

Kill switch on? → refuse
↓
Is it a known tool? Are the arguments valid (pydantic schema)?
↓
Who is asking? (the gateway checks the task and the worker identity itself)
↓
Is the connector (Outlook, web, files...) switched on for this chat/routine?
↓
Scope rules: allowed website? file inside the shared folder? subfolder approved?
↓
Policy engine decides: ALLOW / ASK YOU / DENY (data sensitivity, injection suspicion, risk of the tool, autonomy profile)
↓
Budgets (tokens, web requests, data sent out) and rate limits
↓
DLP: is a secret or private data about to leave? → block
↓
If it needs approval: an approval card appears; you see the exact payload; approval is bound to a hash of it and used once
↓
Re-check everything again right before running (things may have changed while you decided)
↓
Write «about to execute» to the audit log (if logging fails, nothing runs)
↓
Run the tool. Late results are thrown away if you pressed STOP meanwhile.

6. Files: My Files, quarantine and the safe reader

What My Files is for: a private, encrypted shelf of documents the assistant may use (and files it creates for you, like routine reports). It does not summarise uploads on its own - it extracts text, labels sensitivity, flags risks and makes them searchable.

Upload (button, drag, or paste a picture). The name is cleaned (no ..\, no hidden characters, no :).
↓
Quarantine: stored encrypted (AES-GCM, one key per file) - nothing can read it yet.
↓
Checks: real type from the first bytes vs the extension, size, programs/scripts/shortcuts blocked, zip tricks (zip-slip, bombs, passwords, duplicates), Office structure matches the extension, PDF features flagged, pictures checked without decoding (size, frames, hidden data after the end).
↓
Antivirus: Microsoft Defender if on → otherwise Windows AMSI (only if it proves itself on the harmless EICAR test) → otherwise the file waits in Quarantine and you may release it with your password (never if malware was found)
↓
Parse in pa-parser (separate process, limits, no network): text, hidden text is listed separately, active content (macros, scripts) is flagged and ignored.
↓
Pictures and scanned PDFs: if a vision model is set up, it reads the text and describes the picture; a PDF with no text layer is treated as a scan
↓
Ready: text is indexed for search, can be added to My Knowledge, and the AI can read it with files.read. Everything it reads is labelled untrusted.

7. Your own files and folders (read in place)

You press the paperclip (file) or folder button
↓
A dialog shows what the assistant would get (file counts; subfolders are a separate unticked box)
↓
You press Share → a grant is saved for this chat and this app session
↓
The model sees a name and an id - never a path
↓
It calls localfile.digest / browse / text / query; each path is resolved and must stay inside the folder
↓
Needs a subfolder? A card asks you: Allow subfolders / Not now
Rules that cannot be switched off
  • Read-only: nothing is changed, deleted or copied
  • New chat = nothing shared
  • Sign out or restart = approvals expire (Allow again)
  • Never shared: whole drives, your user folder, Windows, Program Files, AppData, .ssh/.aws..., network paths, programs, shortcuts/junctions that lead outside
  • Only you (the UI) can create or widen a grant; the AI cannot

8. Models: four kinds that never mix

Each kind has its own card, list, default and Add button in Settings → AI Model. The gateway refuses a voice model added as a chat model, refuses wrong role assignments, and never uses a wrongly assigned model. After Add the test runs by itself in the background; when it passes the model becomes the default for its own kind if none was set.

9. Voice: long dictation in 30-second pieces

Press the microphone: the window records 16 kHz mono audio in memory (nothing is stored as a file).
↓
Every ~30 s, at a quiet moment (max 40 s) a piece is cut off and sent to voice.transcribe while you keep talking.
↓
The gateway converts/checks the WAV and asks the voice model (Ollama /api/chat with the audio); the answer's language tag is removed.
↓
The text appears in the message box piece by piece; a failed piece is retried; unsent text is kept as a draft.
↓
Press Stop: only the last piece is awaited, then the message is sent (a 9-minute test took 16 s in total).

10a. Memory and file summaries: how the assistant learns about you

Everything is switchable: Settings → Memory (Learn about me automatically) and Settings → Files & Storage (Summarise new files automatically).

You chat / switch on a routine / add a file
↓
A local model reads ONLY the lines you typed (never mail, web or tool output) and proposes up to 3 lasting facts
↓
Code filters: no secrets, no ID/PAN/Aadhaar/card/phone/e-mail values, no duplicates, nothing you already forgot, daily cap
↓
Saved in Memory with its source - visible, editable, Forget-able
↓
Next questions: the assistant is told your learned facts and the ones relevant to what you just asked
You add a file (e.g. PAN card)
↓
After scan + parse, a model writes: title, kind, summary, keywords, kinds of personal data
↓
Code finds ID values itself and removes them from anything the model wrote; the file is raised to CONFIDENTIAL
↓
A memory records where the file is and what it is
↓
Later: «show me my PAN card» → files.find → files.read shows the real file

10. Outlook and routines

Routine vs Mission: same engine, two names. A routine repeats on a schedule (daily mail digest); a mission is usually a one-off goal (research and report). Both only get the tools you allow and anything risky still asks you.

Switch on Local Outlook in Settings → Connectors (classic Outlook only; new Outlook cannot be read).
↓
Email monitoring skills (hourly check, waiting for my approval, VIP mail, deadlines...) are routines: saved read-only instructions with a schedule.
↓
When one runs, the app first fetches the data itself (code, not the model): counts, To vs CC, replied or not, flags like APPROVAL / DEADLINE / URGENT / QUESTION.
↓
The model only turns that data into a short answer. If nothing is new it must answer NOTHING_NEW and you are not disturbed.
↓
Results show on the Outlook screen; a Windows notification is titled with the routine's name.

11. How your data is protected

More detail: docs/THREAT_MODEL.md, docs/SECURITY_AUDIT_2026-10-02.md.

LayerWhat it does
Password + PINPassword is stretched with Argon2id. PIN is wrapped by the PC's TPM chip (or a software key in developer mode only).
Key hierarchyMaster key (random) → wraps the database key, file keys, secrets key. Recovery key (printed once) can rebuild access.
DatabaseSQLCipher: the whole database file is AES-encrypted; settings, chats, memory, secrets are inside.
Audit logAppend-only, each line carries the hash of the previous one (HMAC chain); Verify in Activity shows if anything was changed.
Named pipe + tokensWindow and gateway talk over a local pipe; each side must show a random token and its process id is checked (no pipe squatting).
RolesEach connection has a role (ui / core / worker); each method is allowed for specific roles only. The AI role cannot touch settings, secrets, approvals or the kill switch.
Egress filterGateway-only web access with allow-list, SSRF protection (no private/loopback/metadata addresses, DNS pinning, redirect re-checks).
DLPBlocks secrets, keys, card/ID numbers from leaving; confidential data to remote models needs approval, restricted data never leaves.
STOP ALLKill switch stops the agent, tasks, connectors, web and sandbox within ~2 seconds; releasing needs your password.
Safe displayChat text is sanitised (DOMPurify), links need a click-through, remote images are never loaded, strict content security policy in the window.

13. How a setting change works

Defaults live in code (settings_schema.py). A test changes, reads back and resets every setting automatically.

You flip a switch in Settings.
↓
The window asks the gateway to classify it: is it tightening (safer), loosening (less safe), or neutral?
↓
Tightening / neutral: applied immediately. Loosening: a warning with the risk in plain words, a 10-second read delay and your password
↓
Saved in the encrypted database, logged with before/after values, shown at once. Some settings (like the search provider) also need a fresh re-authentication.
